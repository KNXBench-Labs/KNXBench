# U10 / ISSUE-12 — explicit gateway endpoint, discovery still unproven (2026-09-29)

## Scope and contract

- The existing monitor API accepts a single `gateway` string. `apps/knx-server/src/bus_routes.rs::start_monitor` parses `SocketAddrV4`, and `crates/knx-net/src/client.rs` uses that address type. The web monitor now keeps separately labelled host and port, defaults an empty port to `3671`, validates numeric IPv4 and the port range, and composes the existing string only at the API call. Preferences remain single-string and unsupported legacy values remain visible for correction.
- Discovery still publishes a shared, non-blocking list; selecting an interface fills both fields without connecting. The manual IPv4 endpoint remains usable on an empty/failed search. Help text, English/German labels, the manual, responsive styles and screenshot describe the current controls. No new protocol or package behavior was introduced.
- U2's syscall comparison in `docs/RESEARCH.md` §20.1 and `docs/KNOWN_LIMITATIONS.md` §79 showed successful multicast sends but no receive in both packaged and unpackaged paths. No AppImage-specific mechanism was demonstrated. A wire capture or gateway-side evidence is needed before narrowing or changing the network behavior. The discovery-repair and loopback checklist items in `docs/superpowers/plans/2026-09-21-user-reported-issues.md` remain open.
