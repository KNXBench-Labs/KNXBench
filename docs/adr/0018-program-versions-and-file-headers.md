# ADR 0018: Programs carry SemVer pre-release versions; files carry a one-sentence header and no version

Date: 2026-09-12
Status: Accepted
Session: 7 (T35, versioning and file headers)

## Context

The user asked on 2026-09-12 for two things: every program in the
repository independently identifiable by version, and a reader able to
learn a file's purpose from its first line — the latter phrased as "a
version plus a one-sentence purpose header" per file, with the per-file
version explicitly conditioned on feasibility ("wenn überhaupt machbar").
The project is in its alpha phase: nothing has been released, nothing is
tagged.

What the tree said before this ADR: all 14 Cargo packages (`crates/*`,
`apps/knx-cli`, `apps/knx-server`, `apps/knx-desktop/src-tauri`, `xtask`)
were `version = "0.0.0"`, as were `apps/knx-web/package.json` and
`apps/knx-desktop/src-tauri/tauri.conf.json`. Exactly one thing read any
of them: `crates/knx-etsproj/src/export/schema11.rs` writes
`env!("CARGO_PKG_VERSION")` into `KNX/@ToolVersion` on export, and no
test or fixture asserts that value. Neither binary had a `--version`;
both parse arguments by hand, without `clap`.

What is verifiable mechanically, and what is not — the question that
decides the per-file half:

- A **manifest version** is parsed by cargo and npm (SemVer syntax is
  enforced at build time), mirrored into `Cargo.lock` automatically, and
  after this ADR duplicated nowhere: `tauri-utils` 2.9.3 documents that
  when `tauri.conf.json` has no `version` key "the version number from
  `Cargo.toml` is used" (`src/config.rs`, `Config::version`), so the
  desktop shell needs one number, not two kept equal by discipline.
- A **build identifier** computed from `git rev-parse HEAD` at build time
  is never written by hand and cannot go stale relative to the sources it
  was built from.
- A **per-file version** has no such property. No tool can tell whether a
  given edit "deserved" a bump, nor which of major/minor/patch; a lint can
  check only that the number parses. The one mechanical proxy — "every
  file in `git diff <base>` must have changed its version line" — needs a
  base ref (available on a pull request, not on a push to `main`), still
  cannot judge the *size* of the bump, and guarantees a merge conflict on
  line 1 whenever two branches touch the same file. This repository runs
  concurrent worktrees as a matter of course (`t25-ui-chrome-language` was
  being written beside this slice); a convention that manufactures
  conflicts there is a convention that gets deleted.

What the existing files look like, measured: 166 Rust files, 144 open with
a `//!` module doc, 24 of those with a first paragraph of exactly one line
— every one of the 24 a single sentence ending in a period. Of 60
hand-written TypeScript files under `apps/knx-web/src` (the 11 in
`bindings/` are generated by `ts-rs`), none opens with a block comment;
three borrow Rust's `//!`, four carry a `// <path>` comment, and sixteen
test files start with `// @vitest-environment happy-dom`. Vitest
finds that pragma with a regex over the *whole* file content
(`detectCodeBlock` in `vitest/dist/chunks/index.*.js`,
`/@(?:vitest|jest)-environment\s+([\w-]+)\b/`), not by position, so a
header on line 1 with the pragma on line 2 is safe.

## Decision

**1. Every program has its own SemVer 2.0.0 version, starting at
`0.1.0-alpha.1`.** All 14 Cargo packages and the `knx-web` npm package
carry it in their own manifest; nothing uses `version.workspace = true`,
because the requirement is that programs version independently, and a
shared number would bump fifteen packages for a change in one.
`tauri.conf.json` drops its `version` key so `knx-desktop` has exactly one
source of truth, its `Cargo.toml`.

Bump rule for the alpha phase: when a merged slice changes what a program
does (a binary's or app's user-visible behaviour, a library crate's public
API), the merge bumps that program's `-alpha.N` — one line in one
manifest, in the merge commit. Slices touching only tests, docs or private
internals do not bump. This is a discipline rule, not a mechanical one, and
that is accepted: a missed alpha bump costs little, because the precise
identity of any build lives in the build metadata below, not in `N`. The
pre-release identifier comes off with the first tagged release; that is a
release decision and there is no release, so this ADR does not make it.

**2. Build metadata names the commit, in `--version` output, never in a
manifest.** `knx --version` and `knx-server --version` (also `-V`) print
`<name> <version>+g<short-sha>` — SemVer build metadata, the `g` prefix as
`git describe` uses it. A `build.rs` in each binary package (identical
copies, ~40 lines of `std`) asks `git rev-parse --short HEAD`, tells cargo
to re-run when `HEAD` or the loose branch ref it points to changes, honours
an explicit `KNX_BUILD_SHA` environment variable first (a source tarball or
a Docker build has no `.git` to ask — `.dockerignore` drops it, and the
`Dockerfile` gained the matching `ARG`), and when neither is available
emits nothing, so the build proceeds and prints the bare manifest version.
A sha written into a manifest would change on every commit and turn every
manifest diff into noise, which is why it does not go there. Uncommitted
edits are invisible to it: cargo has no way to watch "dirty".

**3. A file's first line is a one-sentence header saying what the file is
for.** The grammar per language:

```text
Rust        line 1:  //! <One sentence ending in a period.>
            line 2:  either `//!` (blank doc line, more doc follows) or not a `//!` line
TypeScript  line 1:  /** <One sentence ending in a period.> */
```

At most 100 columns (rustfmt's `max_width`, so a header never wraps in an
editor the rest of the file fits in). Exactly one period, at the end. No
second sentence — the boundary heuristic is a `.`, `!` or `?` followed by
whitespace and an ASCII capital letter, so `e.g. Foo` counts as two
sentences and abbreviations stay out of headers. The sentence names the
file's purpose, not its mechanism, and does not start with "This file" or
"This module". The rest of a module doc stays free-form: the header is
line 1, nothing more.

The header applies to files **created or edited from now on**. There is
no repo-wide sweep — the user was explicit — and none is needed for the
lint to be green, because the 24 pre-existing one-line module docs already
satisfy the grammar, and every multi-line one is by construction not a
header (see 5). Where a TypeScript test file needs the vitest pragma, the
header takes line 1 and the pragma line 2.

**4. Files carry no version.** This is the deliberate half-answer to the
request, and the reasoning is the point of this ADR:

- *It cannot be kept honest.* Nothing can check that a number was bumped
  when it should have been, or by how much. A version nobody can verify
  will be wrong within a week, and a wrong version is worse than none: it
  asserts something false with the confidence of a number.
- *It means nothing.* SemVer's semantics — compatibility promises to
  consumers — attach to a released unit. A file's only consumers are the
  other files it is compiled with; there is no compatibility surface for
  `x.y.z` to describe.
- *Git already does it, better.* `git log -1 --format='%h %cs' -- <path>`
  gives any file its last-changed commit and date with no human in the
  loop, and the `+g<sha>` in `--version` pins every file's state at once
  for any built binary. A hand-maintained counter would be a lossy copy of
  that.
- *It fights the workflow.* Bump-on-touch puts line 1 in every diff and
  conflicts it on every concurrent edit of the same file.

What the user actually wanted from the per-file half — "a reader learns a
file's purpose from its first line" — the sentence delivers alone. What a
version would have added — "which state of this file am I looking at" —
the commit sha delivers exactly, and the lint does not pretend to validate
a number it cannot judge.

**5. `cargo run -p xtask -- check-headers` lints the shape of headers
that exist.** It walks `apps/`, `crates/` and `xtask/` for `.rs`, `.ts`
and `.tsx` files, skipping `target/`, `node_modules/`, `dist/` and the two
`ts-rs` output directories — the committed `apps/knx-web/src/bindings/`
and the gitignored default `crates/knx-projection/bindings/` that
`cargo test -p knx-projection` leaves behind, which has to be named or
the lint's counts would depend on whether tests have run on the machine.
A Rust file whose first paragraph
continues past line 1, or a TypeScript file whose line 1 is not a
single-line `/** ... */`, has *no header* and is counted, not failed. A
line 1 that is shaped like a header but breaks the grammar fails the
lint with the file and the reason. A single-line docblock holding only a
pragma (`/** @vitest-environment happy-dom */`) is not a header either.
The lint prints three counts — well-formed, without a header, generated
and skipped — so the convention's spread is visible without anyone
claiming coverage the tree does not have. It runs in CI beside
`check-layering`.

What it deliberately does not do: judge whether the sentence is true or
still current (review does that); demand coverage; or check any per-file
version, because there is none to check.

## Alternatives considered

**One workspace-inherited version** (`version.workspace = true`). Rejected:
the user's requirement is per-program identity, and one number for fifteen
packages would bump all of them for a change in any.

**A per-file version with a `git diff`-based bump lint.** Rejected for the
reasons in Decision 4: it needs a base ref, cannot judge bump size, and
creates line-1 conflicts across concurrent worktrees.

**A per-file version, unlinted — "just add the number and trust people".**
Rejected: the user's own condition was feasibility, and a number nobody
checks is precisely the wrong-version case this ADR exists to avoid.

**A version derived from git tags (`git describe`) instead of manifests.**
Rejected: there are no tags, and cargo and npm consume the manifest field
regardless — the manifest is not optional, so it has to be right.

**A build-info dependency** (`vergen`, `built`, `git-version`). Rejected:
each is a supply-chain addition and a `cargo deny` surface for what forty
lines of `std::process::Command` do, and none of them would have been
allowed to write into a manifest anyway.

**`clap` for `--version`.** Rejected: both binaries parse arguments by hand
today; a dependency to print one line is out of proportion, and the hand
parser gains one match arm.

**Keeping `version` in `tauri.conf.json` and linting it equal to
`Cargo.toml`.** Rejected: deleting a duplicate is simpler than checking it,
and Tauri documents the fallback.

**Enforcing header coverage on the files a branch changed.** Deferred, not
rejected: it needs a base ref, so it would be a pull-request-only check,
and review carries the rule today. If the "without a header" count does
not fall as files are touched, this is the next step.

**A multi-line header** (the whole first paragraph as the header).
Rejected: the user asked for the *first line*, and a one-line first
paragraph is the only structural mark that separates a header from a
pre-convention module doc without inventing a tag like `//! @header`.

## Consequences

- Every manifest reads `0.1.0-alpha.1`; the exported `KNX/@ToolVersion`
  now says so too. No fixture or test asserted the old `0.0.0`, and none
  asserts the new value literally — `apps/knx-cli/tests/cli_version.rs`
  and `apps/knx-server/tests/bin_version.rs` check `--version` against
  `CARGO_PKG_VERSION` and that the metadata, when present, is `+g<hex>`;
  `cli_version.rs` additionally fails if the manifest version ever loses
  its pre-release identifier before anyone means it to.
- Two identical `build.rs` files. Accepted: a shared build-support crate
  for forty lines was judged a worse trade than the duplication, and the
  files say so.
- The 24 pre-existing one-line module docs became valid headers by
  coincidence, which the lint confirms rather than assumes. 201 files have
  no header today; the number is printed on every run and is expected to
  fall as files are touched. Nobody is asked to sweep.
- The sentence-boundary heuristic is stated, so a false positive (`e.g.
  Foo`) is a documented "reword the header", not a mystery.
- `--version` says which commit, never whether the tree was clean. Anyone
  bisecting from a `--version` string is looking at that commit plus
  whatever was uncommitted at build time, and this ADR tells them so.
- Enforced: `check-headers` in CI; the two `--version` tests; cargo's own
  SemVer parsing on every manifest. Not enforced, and said so: the alpha
  bump rule, and the truth of any header sentence.
