# ADR 0175: Device configuration modules are declarative data

Date: 2026-11-15
Status: Accepted (format, engine and CLI in WP-42.1; storage and editor follow)
Session: WP-42.1

## Context

Devices running their own firmware can carry configuration that is not an ETS
application parameter: a menu tree, key assignments, LED policies. The owner
wants KNXBench to configure such data and wants KNXBench to stay "modular and
simple" to extend (owner decision, 15 November 2026). Earlier decisions already
set the frame: an extension is data, never executed code
([ADR-0025](0025-extension-is-data-not-code.md)); manufacturer and product data
live in a separate, versioned database ([ADR-0005](0005-separate-product-database.md)).

The first consumer is a replacement firmware for one device's operating unit,
maintained outside this repository. Its configuration format has a strict
validator in the firmware itself: typed fields, cross-references between
tables, a tree with bounded depth, pairing rules and a binary encoding with
length and CRC. Writing that validator again in KNXBench as Rust would put
device-specific code into KNXBench and would need a KNXBench release for every
firmware format change.

## Decision

1. A **device configuration module** is a JSON package: a typed document schema,
   rules written as JSON expression trees, and binary export layouts
   ([contract](../contracts/device-configuration-modules.md)). One generic crate,
   `knx-devconf`, loads modules, validates documents and produces exports. It
   has no knowledge of any device.
2. The engine is pure: no I/O, no project types, deterministic output, explicit
   size and evaluation limits. Callers (CLI now, server later) own files.
3. The module format refuses unknown members and unsupported versions instead
   of ignoring them, so a module never loads with part of its meaning dropped.
4. Rule violations are reported, never repaired. Export runs only on a valid
   document.
5. Module packages are versioned and identified by `id`, `version` and SHA-256.
   They belong to the product-data layer, not to a project. A device's
   configuration document belongs to the project (WP-42.2), stored with the
   module identity it was written for.
6. Device modules with private or unpublished formats are maintained with their
   firmware, not in this repository. KNXBench's own tests use fictional modules.

## Alternatives considered

- **Rust code per device.** Simplest for the first device, but every device and
  every format change becomes a KNXBench code change and release; contradicts
  ADR-0025 and the owner's modularity request.
- **JSON Schema plus a scripting language** (for example embedded Lua or
  WebAssembly). Expressive, but adds a runtime, a sandbox and a dependency
  surface; a script is code, and its results are harder to explain to a user.
- **A textual rule language.** Friendlier to write, but needs a parser,
  precedence rules and error recovery. JSON expression trees need none and can
  be generated by tools; a text syntax can still be added later as a front end.
- **Calling the firmware's own compiler.** Exact by construction, but requires a
  device-specific toolchain at runtime. It is used instead as the external
  oracle for the module's differential tests.

## Consequences

- New devices need a module file, not a KNXBench release, as long as their
  format fits the declared types, rules and layout items. A format that does not
  fit needs a new engine feature with its own tests, decided separately.
- A module author's claim that a valid document is accepted by the device has
  to be evidenced outside KNXBench, typically by differential tests against the
  firmware validator. KNXBench claims only that it applies the module as written.
- The expression semantics (`null` handling, overflow, limits) are part of the
  format and covered by unit tests; changing them requires a new
  `format_version`.
- The term "module" in this sense is distinct from ETS application modules
  (ADR-0013); documentation and UI say "device configuration module".
