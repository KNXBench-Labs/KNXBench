## Sources and method

Inspected the official *KNX Project Schema23 v01.00.00*, especially the
DeviceInstance attributes, and RFC 3629 §3. The project schema documents
project fields; it is not the manufacturer application grammar.[1]

Public searches covered the exact terms `ParameterByteOrder`,
`TextParameterEncoding`, `LoadedImage`, `LittleEndian`, and combinations with
parameter layout, UTF-8 length and differential download. Official help-centre
release-note and parameter-type pages were candidates, not admitted evidence:
full article retrieval failed; search snippets are not an encoding contract.
The configured extraction backend refused URL extraction; direct public article
requests failed, and browser recovery was unavailable because the user's running
browser held its profile. No browser was stopped and no configuration changed.
A missing search result establishes only this bounded search's outcome, not
that no specification exists anywhere. The retained public schema was inspected;

## KL-170: little-endian parameter images

**Result: specification gap remains.** No inspected public source in this pass
establishes KNX manufacturer `ParameterByteOrder` placement for signed/unsigned

Neither a name containing “LittleEndian” nor a project's successful import is
an encoding rule. Existing `build_download_image` refusal stays unchanged.

To proceed: obtain a source defining per-type placement and interaction with

changing the encoder. This task grants no hardware confirmation authority.
A generic octet reversal would not resolve the missing type/layout contract.

## KL-171: UTF-8 text fields

RFC 3629 defines Unicode encoding using one-to-four-octet sequences, with
restricted lead and continuation forms; this is an encoding definition, not
KNX field-capacity or termination policy.[2]

**Result: specification gap remains.** No inspected KNX source establishes
whether a text field's declared size counts characters or octets, whether
termination reserves storage, padding rules, or whether overflow is rejected
or truncated. Valid UTF-8 alone cannot settle those policies. Existing refusal
of unsupported `TextParameterEncoding` remains unchanged.

To proceed: obtain the KNX field contract and test ASCII, multi-octet boundary
characters, absent/exact/excess capacity, termination/padding, malformed input
and complete-sequence handling. Do not silently truncate or substitute a default.

## KL-172: stored loaded images

Project Schema23 types DeviceInstance `LoadedImage` and `CheckSums` as optional
`xs:base64Binary` attributes, associated with the last download and differential
operation. That identifies a source field's purpose, not the decoded payload's
layout or validity as KNXBench download input.[1]

**Result: payload contract remains undocumented in the inspected sources.**
No accepted source in this pass defines compression framing, decoded records,
address regions, masks, checksums or a comparison algorithm. Base64 typing
alone does not specify compression. A release-note search hit is not a format
specification. No private bytes were inflated or decoded in this research pass.

To proceed: obtain the actual format and scope contract, plus independently
created bounded vectors and malformed-input controls. Retain source unchanged;
do not use a stored image as a download authority or a substitute for evaluated
parameters. A controlled hardware comparison would need separate owner authority
and is not part of this task.
