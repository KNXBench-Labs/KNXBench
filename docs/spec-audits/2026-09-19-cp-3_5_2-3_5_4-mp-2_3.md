Read-only audit, 2026-09-19, opus, reading `03_05_03 Configuration Procedures`,
`03_05_02 Management Procedures`, `03_05_01 Resources`, `03_03_07 Application

## Gaps

### GAP-2.1 — step 11 cannot distinguish "no keys required" from "keys not sent" — *completeness*

> CP §3.5.2, p. 44: `11 Modifying access keys | Set access keys as required` —
> `12 Disconnect | Disconnect via bus`

> AL §3.5.8, p. 129: *"The A_Key_Write.req primitive shall be applied by the
> user of Application Layer, to modify or delete the key associated to a
> certain access level in the communication partner."*

> MP §3.6.1 `DM_SetKey_RCo`, p. 77: *"If the level returned in A_Key_Response
> is not the same as in the A_Key_Write, the operation was not successful.
> Possibly an authorization is required."*

`download.rs:490-495` records step 11 as `"modify access keys (not
implemented)"` and sends nothing; `procedure.rs:312` carries it as a
`StepEffect::Guard`. No `A_Key_Write` encoder exists — `cemi.rs:2167` asserts
the APCI constant exists *without* one.

*"as required"* makes an empty step 11 conforming **when the plan requires no
keys**. The defect: `DownloadPlan` has no field in which keys could be
required, so the report reads identically either way. A download that silently
leaves a device on the installer's default key is a security-relevant silent
difference.

### GAP-2.2 — `unload()` is a download-unload, not a device-unload — *traceability*

> CP §3.5.4, p. 57: `07 Unload IndividualAddress | Set
> SerialNumber_IndividualAddress_Write(FFFFh) via broadcast — Check if
> SerialNumber_InidividualAddress_Read() == FFFFh (via broadcast)`

`download.rs:597-622` implements 01-06 and says so at `:591-597`; `procedure.rs`
declares `source: "CP §3.5.4 steps 01-06"`. The omission is sound — step 07
makes a device unaddressable by design — but `ProcedureKind::Unload` and the
report say "unload" unqualified.

**Erratum in the Standard:** §3.5.4 step 05 says *"For details of the unloading
process refer to the routines of 'Unload Device' in 3.5.1.3"*. CP §3.5.1.3 is
titled **"Memory architecture"**. The string `Unload Device` occurs exactly once
in the whole CP document — in that cross-reference. Both knowledge bases
searched; the reference is dangling and nothing is being missed.

**Three different orders.** §3.5.2 step 05 unloads AP2, AP1, GOT, Association
Table, Address Table. §3.5.4 step 05 unloads Address Table, Association Table,
Object Table, AP2, AP1. §3.5.2's *load* order 06-10 is AP2, AP1, GOT, Address
Table, Association Table. The code iterates `plan.parts` in one order for all
three and cannot match all three clauses. Cosmetic for the unloads (freeing is
order-independent), traceability for the trace.

### GAP-2.3 — `recovery()` is the project's own invention; its `source` says otherwise — *traceability*

`procedure.rs:552` reads `source: "spec §9.1"`; `download.rs:624` opens
`/// Spec §9.1, recovery after an interrupted download.`

**The Standard prescribes no recovery procedure.** Searched both bases:
`recovery` → `[]` in the programming base, 2 unrelated `BusReturnMod` hits in
full179; `interrupted download` → `[]` / `[]`; `restart procedure download` →
`[]` / `[]`. Sanity-checked: `load state`, `download`, `Verify Mode` all return
hits, so the empties are real.

The whole of what the Standard says:

> MP §3.1, p. 68: *"General Exception handling — In general if an error is
> detected, the download shall be interrupted and an error-message shall be
> raised. If there is another exception handling for a device Management
> Procedure, this is stated in the description of the procedure."*

No obligation to leave the device in a defined state, no rollback, no
resumption. (MP §8.1.2, p. 194, is scoped to File Transfer Procedures.) The fix
is one string: `source: "KNXBench design spec §9.1 — no Standard equivalent"`.

### GAP-2.4 — `NM_IndividualAddress_Write` step 2 time-out is 1 s, not 3 s — *correctness*

> MP §2.3, p. 14, step 2 remark column: *"time-out: 1 s"*

The 3 s belongs to MP §2.2 `NM_IndividualAddress_Read`, p. 12: *"time-out:
3 s"*. `procedure.rs:211-215` says *"wait out the full 3 s time-out"*. The
"wait out the full time-out" and "count distinct addresses" halves are right:

> MP §2.3, p. 15: *"to 2.: The Management Client shall always wait until the
> time-out has elapsed. It shall collect all the responses during this
> time-out."*

> MP §2.2, p. 13: *"If two or more responses with the same Individual Address
> are received, there is more than one device with the same Individual
> Addresses."* / *"The Management Client shall not evaluate Layer-2
> repetitions."*

Only the quantity is wrong.

### GAP-2.5 — step 1 aborts where MP §2.3 requires continuation — *correctness*

`procedure.rs:202-206`: *"any answer means the address is occupied and the
procedure stops"*.

> MP §2.3 exception handling, p. 15: *"to 2.: … • A device with the Individual
> Address IA_new to be assigned exists, but it is not the one that is in
> Programming Mode. ⇒ The Management Client shall not continue with the
> Management Procedure. • A device with the Individual Address IA_new to be
> assigned exists, and it is the one that is in Programming Mode. ⇒ The
> Management Client shall continue with the Management Procedure. • No device
> with the Individual Address IA_new to be assigned exists. ⇒ The Management
> Client shall continue with the Management Procedure."*

> MP §2.3, p. 15: *"to 1.: … The Management Client shall continue with the
> Management Procedure in every case."*

Occupancy alone must not stop the procedure. Re-assigning a device to the
address it already holds is the middle bullet and is explicitly permitted —
which is what step 3 guards with `if IA_new != IA_current` (p. 15). See Q2.1:
the clause contradicts itself.

### GAP-2.6 — nothing in `crates/` implements the individual-address write path — *completeness*

Exhaustive grep. What exists: the declarative 4-step list
(`procedure.rs:195`), the codec (`ApplicationService::IndividualAddressWrite` /
`IndividualAddressRead` in `cemi.rs`), and `WriteScope::IndividualAddress
Programming`, whose only non-test reference is `procedure.rs:135`.
`ManagementSession` has no method that writes an individual address.

Not a defect — but `Procedure::for_kind` advertises the procedure, so a UI
enumerating procedures offers one that cannot run.

### GAP-2.7 — no `A_Restart` sender anywhere — *completeness* now, *correctness* once step 4 exists

> MP §2.3 "Use", p. 13: *"The procedure shall check if the programming is
> successful and shall deactivate the Programming Mode by executing a restart
> of the device."*

Step 4, p. 15: A_Connect → A_DeviceDescriptor_Read(00h) → response →
*"A_Restart-PDU"* → *"Abort the connection of the client side Transport
Layer."*

`ApplicationService::Restart { response, restart_type, data }` exists in
`cemi.rs` with reserved-bit validation and `InvalidRestartType` for type > 1.
`WriteScope::Restart` exists in `mutation.rs`. The only non-test reference to
either is `commissioning.rs:2641` — a test. A device left in Programming Mode
after a failed write stays there.

### GAP-2.8 — `set_programming_mode` is implemented and unreachable — *completeness*

`commissioning.rs:1817`; its three callers (2183, 3035, 3057) are all inside
`mod tests` (begins at 1922). The implementation is right:

> MP §3.13.2 `DMP_ProgModeSwitch_RCo`, pp. 94-95: connection oriented, *"The
> Programming Mode shall be realised as 'Programming Mode – Realisation Type
> 2'"*, A_Memory_Read(60h,1) then A_Memory_Write(60h,1), remark *"In the data
> (DD) bit 0 has to be set according to the mode. The parity (bit 7) has to be
> calculated."*

`prog_mode_write(old, enable)` does `old XOR 10000001b` and writes only if the
bit actually changes.

### GAP-2.9 — the transport repeats one time fewer than permitted — *correctness*, minor

> TL §3, p. 15: *"If no acknowledgement is received or if the acknowledgement
> is a negative acknowledgement, the local Transport Layer shall repeat the
> transmission of the T_DATA_CONNECTED_REQ_PDU up to 3 times with an
> acknowledgment time-out time of 3 s."*

> TL §4, p. 16: `connection timeout: time interval of 6 s` / `acknowledgement
> timeout: time interval of 3 s` / `max_rep_count 3; maximum of T_Connect.req
> repetitions`

`commissioning.rs` `exchange_inner`: initial send sets `attempts = 1`, loop
bails at `attempts >= MAX_REP_COUNT`. Maximum transmissions = 3, i.e. the
original plus **2** repetitions; the clause permits 3 repetitions = 4
transmissions. The constant is named after the Standard's but used as a
transmission cap. A device that would have answered the third repeat is
abandoned as `SessionError::NoAnswer`.

### GAP-2.10 — the load-state wait omits the "once more" attempt — *correctness*, minor

> RES §4.23.2.4.1, p. 297: *"If a before established TL-connection breaks down,
> the MaC shall try to re-establish the connection periodically during the
> maximum transition time and once more when the maximum transition time has
> passed."*

`wait_for_load_state` reconnects inside the loop, citing this clause, but
returns `TransitionTimedOut` immediately at `started.elapsed() >=
max_transition`. The clause asks for exactly one more attempt.

## What is already correct — write no tasks for these

- **Memory chunking.** `knx-core/src/commissioning/memory.rs`: limit from
  `PID_MAX_APDU_LENGTH` minus 3, default 12 when absent, 255 as ESCape Code,
  Router-Object-only value refused, cap 63. Matches AL §3.5.4 p. 111 (*"to
  write between 1 octet and 63 octets"*), AL §3.5.4 p. 113 (*"shall ignore the
  A_Memory_Write.ind if the value of the parameter 'number' is greater than
  Maximum APDU Length – 3"*), RES §4.3.7.2.1 p. 46 (*"maximal 15 octets"* when
  the property is absent), RES §4.3.7 footnote 4 p. 46, RES §4.3.7.2.2 p. 46.
  The extra `USER_MEMORY_MAX_OCTETS = 15` cap catches something the project's
  own design spec §6.4 got wrong.
- **Verify Mode, both branches.** Empty `A_Memory_Response` as refusal per AL
  §3.5.4 p. 113; T_ACK wait in the inactive branch per AL §3.5.4 p. 112.
- **Verify Mode asserted on every connect**, reconnects included — RES
  §4.2.14.7.4, p. 35.
- **`PID_ERROR_CODE` read before anything is unloaded** (`download.rs:624-640`)
  — RES §4.2.28, p. 40: *"When the load state changes from 'Error' to a
  different state then the Error Code shall be set to '0'."* The best-reasoned
  part of `recover()`.
- **Load-event writes wait for the state**, and a state RES Table 94 forbids is
  reported as `IllegalTransition` rather than waited out.
- **`LoadCompleting` silence tolerated** — RES Table 93, p. 295.
- **Allocation outside `Loading` checked, not assumed** — CP §3.5.1.2 Table 4,
  p. 39.
- **§3.5.2's step numbering matches the clause exactly**, 1-12 including the
  part order of 06-10, and `download.rs:469` continues past 10 for plans with
  more than five parts rather than stopping.
- **The PL110-only footnote is honoured** (§3.5.2 step 09, footnote 7, p. 44).
- **`unload()` numbering 1-6** matches CP §3.5.4 01-06 exactly.
- **Access levels inverted correctly** — 0 is maximum access, `FFFFFFFFh`
  rejected as a key, any octet accepted against the 4-or-16-level ambiguity;
  AL §3.5.7, p. 127.
- **Whole-procedure retry correctly absent** — see Q2.5.

**Documented execution-order deviation, not a defect:** `download.rs:716-740`
records step 1, then 3, then 2, then 4 because `connect()` authorises as it
connects; the test pins `vec![1, 3, 2, 4, 5, 6, 7, 11, 12]`. Nothing in §3.5.2
makes the DD read a precondition of the authorise.

## Open questions

**Q2.1. MP §2.3 contradicts itself on an occupied `IA_new`.** Body p. 14: *"if
A_Disconnect-PDU is received then IA_new shall be regarded as occupied; end
procedure."* Exception "to 1." p. 15: *"shall continue … in every case."*
Exception "to 2." then makes continuation mandatory in two of three cases.
Auditor's reading: implement the exception text (more specific, later) and
surface the occupancy to the operator. Not resolvable from the PDF alone.

**Q2.2. RES §4.23.2.4.1 p. 297** says *"continue with further access only after
load state has changed to LoadCompleted"* — but Table 92 names the state
`Loaded`; `LoadCompleting` is the intermediate; `LoadCompleted` is a Load
Control value (02h), not a state. Editorial slip; the code assumes `Loaded`.

**Q2.3. CP §3.5.4 step 05's cross-reference is dangling** — see GAP-2.2.

**Q2.4. Is any in-scope step mandatory for System B but absent entirely?**
`System B mandatory` returns `[]` in both bases. Neither §3.5.2 nor §3.5.4
marks a step optional or profile-conditional except §3.5.2 step 09's PL110
footnote. The question belongs to `06 Profiles v02.01.01.pdf`, outside this
audit's four PDFs.

**Answered, 2026-09-19 (task C18, `06 Profiles v02.01.01.pdf` opened).** No.
Volume 6 Annex A §A.2.1 (S-Mode End-devices Interface Object list, p. 137)
marks Device Object, Address Table Object, Association Table Object and
Application Program Object all `M` for masks 07B0h and 17B0h (System B); every
Property CP §3.5.2/§3.5.4 actually reads or writes on those objects —
`PID_LOAD_STATE_CONTROL` (5), `PID_MANUFACTURER_ID` (12),
`PID_TABLE_REFERENCE` (7), `PID_MCB_TABLE` (27) — carries a mandatory-existence
symbol (`m/x` or `m/n` family, never `x`) for those same masks in Annex A's
per-object tables (A.2.4, p. 143; A.2.5, p. 145). Nothing in Annex A adds a
System-B-mandatory Property or object these two clauses' step lists leave
untouched, and nothing marks a step CP already lists as forbidden for System
B. This closes task J without a code change: no missing mandatory step
found, confirming the search-based finding above with a direct table read.

**Q2.5. Does the Standard require a retry distinct from retrying a whole
procedure?** Answered, and the code is right: only the transport-level
repetition (TL §3/§4, GAP-2.9) and the **one** extra application-layer attempt
after a Master Reset Process Time expires (MP §3.7.1.2.2, p. 81). No
procedure-level retry obligation anywhere; MP §3.1 is the opposite of one.
`recovery()`'s *"no retry loop: a failed recovery is reported as one"* is
correct and should keep that comment.
