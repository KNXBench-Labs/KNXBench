## #17 — positional templates reach channel/object labels

The screenshot shows `{{0:Page 1}}` in a channel heading and
`Page 1 - {{0:Icon 1}}` in object names. This is not enough to establish the
reporter's proposed classification as translation fragments.

Verified source boundaries:

- `crates/knx-productdb/src/dynamic/evaluate.rs:1931–1942,2119–2140,2167–2174`:
  substitution supports named module arguments. The argument-name predicate
  rejects numeric-leading/colon-containing names, so `0:Page 1` is retained
  literally. Numeric text parameters are explicitly outside that mechanism.
- `crates/knx-productdb/src/query.rs:863–868`: channel translation lookup returns
  stored templates; a caller must perform any supported substitution.
- `crates/knx-app/src/com_object_language.rs:119–125`: translated product-layer
  names/descriptions can overlay display values; user/instance text is protected.
- `docs/limitations/KL-003-parameter-evaluation-and-editing-boundaries.md:225–248`
  already documents the unimplemented numeric/TextParameterRefId family.

Thus source tracing explains the displayed syntax; no actual GVS template
resolution was exercised. The default-text/parameter-reference rules for this
specific `{{index:default}}` form remain to be evidenced. Do not present a
colon-split/brace-stripping frontend workaround as verified ETS semantics.

### Goal B request (suggest B14; its ordering)

Research positional/default rules using permitted primary material and bounded
corpus observation; document evidence and unsupported cases before implementation.
Resolve supported text in the product/application projection, not independently
in each UI. Keep raw templates, provenance and user-edited names. Channel titles,
object names, search and documentation should agree. Distinguish an actual
parameter-derived value from an explicit display-only default fallback.
Missing references, malformed tokens and unsupported forms must remain visible
as such; do not fabricate parameter values or erase raw source information.

Tests: synthetic default/custom/missing parameter values, language changes,
multiple placeholders, colon/Unicode/default edge cases, malformed input,
module-scoped references, display budgets, preservation/roundtrip and user-layer
precedence. Full resolution may need an application/model dependency; do not
promise it merely because labels can be cosmetically cleaned.

Acknowledgement `6154991930` read back exactly; assigned `KNXBench-Labs`, label
`bug`. Public plan is the evidence-gated work above, with no fix/release date.

## #18 — known device selection waits for download-status response

`apps/knx-web/src/DeviceDownloadPanel.tsx:77–89` builds selectable devices from the
already available project tree, not a remote device-list query. At :108 the first
status check starts as `checking`; :174 defers the handoff until that check ends.
`poll()` (:214–227) fetches `/api/device-download/status`; :187–192 applies the
requested device only afterward. No `statusCheck` loading state is rendered in
the JSX. Same dependency and missing status indication in alpha.11 and inspected
main source.

A throwaway synthetic component probe held `pollDeviceDownload` pending:

```json
{"selected":"","statusCalls":1,"planCalls":0,"startCalls":0}
```

The immediate-selection assertion failed exactly (`expected '' to be '10'`).
A control test rejected the pending request with the normal no-download `404`;
the same device then appeared, with zero plan/start calls. Existing preparation
tests: 25/25 pass; control probe: 1 pass; new expected-failing visibility probe:
1 fail. Command: `npm test -- src/Issue18.repro.test.tsx src/DeviceDownloadPreparation.test.tsx`.
The probe/dependency symlink were removed; no app source/test change was committed.

This establishes the UI wait, **not** a measured 30-second delay on the reporter's
system. Backend `apps/knx-server/src/device_download_routes.rs:581–605` uses
`try_lock` on the download session, returning conflict rather than waiting for
connection timeout. Readiness is a separate request; its route
`device_readiness_routes.rs:64–74` synchronously computes project-wide readiness
under project/product locks. Timing/runtime contention is a candidate to measure,
not an established cause of this reporter's delay.

### Goal B request (suggest B15; its ordering)

Show the requested device immediately as **context**, separately from admission
to change an active download target. Show pending status/readiness and clear retry/
errors. No invented progress percentage or ETA. Preparation/start remains gated
until the status is safely known; preserve running/connecting/unknown checks,
project-incarnation and missing/addressless-device guards, stale-plan invalidation
and late-response isolation. Do not solve the empty UI by weakening bus safety.
Measure status/readiness latency separately before performance changes.

Tests: delayed/unavailable/conflicting replies, active download, repeat navigation,
project/device changes, readiness updates and zero plan/start mutations during
navigation; browser visibility evidence. No hardware needed for these UI tests.
