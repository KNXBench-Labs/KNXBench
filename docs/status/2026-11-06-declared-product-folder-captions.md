# Literal installed-product folder declarations

## Scope

The bounded WP-06 implementation adds optional **current installed-product
literal declarations** to an already assigned saved project-folder path. It
neither reconstructs current placement nor establishes the product bytes used
at original import. The [identity/text contract](../contracts/declared-product-folder-captions.md)
and [primary-source study](../research/2026-11-06-product-folder-captions.md)
separate those authorities.

The source policy admits project schemas 20 and 23 with measured retained
product XML namespace project/20. This is a finite software policy, not general
schema/manufacturer compatibility. Saved-folder refusals remain authoritative;
module-instance placement, Repeat expansion, aliases, translations, templates,
renames, staleness after parameter edits and object priority remain outside scope.

## Display and data integrity

- Existing admitted saved `text` keeps precedence, including explicit empty and
  whitespace-only fields and their ID fallback. Only otherwise can a separately
  admitted literal product declaration accompany a Folder ID.
- Source kind, exact application/PB identifiers and source SHA-256 remain separate
  optional metadata. UI badges distinguish the declaration from saved text;
  local source paths are never exposed.
- IDs, complete saved paths, grouping keys/order, activation/refusals, expansion
  and editor ownership do not depend on labels. Equal declarations do not merge
  folders. HTML-looking strings render as plain text.
- Search includes only the selected Folder display label, not hidden/unsupported
  metadata or product text superseded by saved text.
- The field is read-only and not persisted into the project or opaque import
  source. Native save/open and edit/undo retain original project/history/source
  authority. No domain/storage/import schema or product-DB migration is added.

## Resource admission

Source bytes, XML work/structure, candidate identities, identity-admission
metadata, normalized corroboration and retained/repeated DTO copies have finite
budgets. Identity admission must not construct the general diagnostic candidate,
path, package or unavailable-reason report. Normalized corroboration must use a
bounded pass, not one full Dynamic scan per caption. The reader constants and
registered regressions define the executable ceilings.

The identity ceilings bound relevant evidence populations and materialization;
they are not a global SQLite VM deadline for unrelated conflict rows under the
unchanged catalogue schema. Normalized corroboration independently bounds its
visited scope rows and inspected metadata.

Optional resource/ownership/source refusal leaves the saved-folder presentation
intact. Copy exhaustion applies no partial overlay and emits the existing bounded
generic diagnostic. Actual database faults retain normal error handling.
