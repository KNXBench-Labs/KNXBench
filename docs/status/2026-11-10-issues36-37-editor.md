## Source-bound diagnosis

### #36: same device after leaving Download

`App.selectEntity` resets the detail, starts `deviceDetail`, and admits only the
latest request for the currently selected device. The existing maintained
`ga-members-download.e2e.ts` already navigates Download → Devices → the same
editor; all 23 original cases passed on unchanged production source.

Opening Download also starts `deviceReadiness` automatically.
`device_readiness_routes::readiness` holds the project lock and catalogue read
lease while `project_readiness` prepares every eligible project device. A new
editor's backend detail read can wait there even though no download was started.
Navigation does not cancel that computation. This is a concrete blocking path,
**not evidence of an infinite computation, lock cycle, or retained bus ownership
fault**. This candidate does not change that backend behavior or add a timeout.

The added full-App browser case characterizes navigation while the retained
status request is pending, then replaces a pending editor GET with another
activation of the same device and completes the stale GET afterward. It sends
no plan/start request. It is API-fixture coverage, not a reproduction of a
backend readiness stall and not a demonstrated fix for the original hang.

### #37: overlapping ordinary parameter saves

Each `ParameterFieldRow.apply` owns its own promise and releases `saving` in
`finally`. That promise awaits the HTTP POST, **not background-journal
acknowledgment**. A revision conflict is reported and reloads the current tree;
only the user's explicit retry may resubmit. Journal coalescing has not been
shown to strand either field.

One related frontend lifecycle defect was reproduced against unchanged base
source: an earlier successful POST could replace the shared panel with an older
snapshot after a newer explicit-retry success. The actual App rejects that older
tree, so no tree update necessarily triggers a healing panel refetch. The
regression uses an admissible sequence: A commits revision 2 with its reply
delayed; B's revision-1 POST receives 409; an explicit retry binds to revision 2
and commits revision 3; A's revision-2 reply arrives last.

An initial second proposed defect (global tree publication after editor
retirement) was rejected by independent review: the committed command still
belongs to App. Suppressing its callback would lose the latest revision,
modified state and Undo availability after navigation. The candidate preserves
that publication through App's existing authority guard while fencing only the
retired row's local updates. The incorrect original test oracle is retained as
an uncredited failure, not a reproduced product defect.

The demonstrated stale-panel defect justifies this bounded hardening. It does
**not** establish why both original fields remained saving for minutes.

## Candidate changes and invariants

- Local row publication, errors and busy cleanup belong to a mounted
  device/language/field owner. Every successful ordinary standalone-row command
  still forwards its authoritative tree to App, whose lifetime/revision guard
  admits it or refuses an older result; retirement must not lose a newly
  committed command. The separate object editor's mutation boundary retains
  its existing post-retirement suppression contract.
- The shared parameter reader fences retired GETs and pre-write reads. Complete
  snapshot identities prevent older or foreign write panels from replacing the
  newer current panel; a revision refresh preserves mounted rows and drafts.
- Conflict reload publication belongs to the mounted reader owner and target.
- Existing server validation, expected-value/revision bindings, explicit retry,
  domain commands, Undo/Redo, journaling and retained operation ownership remain
  unchanged. There is no automatic retry, arbitrary timeout or bus operation.
