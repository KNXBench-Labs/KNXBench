## Task 1 — codec foundation and the datapoint types of one octet or less

**Files:** `crates/knx-core/src/dpt.rs` → `crates/knx-core/src/dpt/mod.rs`
(move), new `crates/knx-core/src/dpt/codec.rs`,
`crates/knx-core/src/lib.rs`, `crates/knx-net/src/cemi.rs`,
`crates/knx-net/src/lib.rs`.

1. **Move `GroupValue` down** (spec E4-D2). Delete the `GroupValue`
   definition from `crates/knx-net/src/cemi.rs` and define it in
   `knx-core`'s `dpt` module, doc comment and all, adjusted so it no
   longer refers to a "cycle". Re-export it from `knx-core`'s `lib.rs`
   next to `DptRef`, and from `knx-net`'s `lib.rs` with
   `pub use knx_core::GroupValue;` so that line 22's existing export list
   keeps working. No call site in `cemi.rs`, `client.rs`,
   `tests/live_gateway.rs` or `apps/knx-cli` should need an import
   change; if one does, that is a signal the re-export is wrong, not a
   licence to edit the call site.
2. **Split `dpt.rs` into a module directory.** `dpt/mod.rs` keeps
   `DptRef`, `DptParseError`, their tests and the new `GroupValue`, and
   declares `mod codec;` with the public re-exports. Moving code is not
   an invitation to change it: `DptRef::parse` and its tests stay
   byte-identical apart from the module path.
3. **Fix the APCI corruption** (spec E4-D3). In
   `crates/knx-net/src/cemi.rs`, `encode_group_value` must not let a
   `GroupValue::Short(v)` with `v > 0x3F` reach the `apci_lo`
   computation on line 238, where its top two bits overwrite the APCI.
   Promote such a value to a single octet instead. Add a test that
   encodes `GroupValueWrite(GroupValue::Short(0x40))`, decodes the
   resulting frame, and asserts the service is still a `GroupValueWrite`
   carrying the value 0x40 — today that assertion fails.
4. **Add `DptValue` and `DptCodecError`** exactly as the spec's E4-D4 and
   E4-D5 describe, in `dpt/codec.rs`, with `Display` for both and
   `std::error::Error` for the error, matching the style of
   `DptParseError` in the same crate.
5. **Implement `decode` and `encode`** for main types **1, 2, 3, 5, 6, 7,
   8**. Signatures:
   ```rust
   pub fn decode(dpt: DptRef, payload: &GroupValue) -> Result<DptValue, DptCodecError>;
   pub fn encode(dpt: DptRef, input: &str) -> Result<GroupValue, DptCodecError>;
   ```
   Points that decide correctness, each to be resolved against the
   Standard and cited, not guessed:
   - Which of these types travel in the six inline bits and which get
     their own octet. Encode must produce the form the Standard
     prescribes. Decode must accept the prescribed form, and must also
     accept the other form rather than rejecting a real telegram — but
     only where the bit width still fits.
   - Main type 3's `B1U3` layout: which bit is the direction, which bits
     are the step code, and what step code 0 means.
   - Main type 5's scaled subtypes versus its raw counts: branch on the
     subtype for exactly the subtypes the Standard scales, and for no
     others. State in a comment which subtypes those are.
   - Main type 1's subtype changes nothing about the encoding. Say so in
     a comment so the next reader does not go looking.
   - `DptRef` with `sub: None` (e.g. `DPT-5`) means "main type, no
     subtype selected". Decide and document what that does for a main
     type whose subtypes scale differently — the honest answer is
     probably the unscaled raw form, but say which and why.
   - Text input parsing for `encode`: booleans accept
     `on`/`off`/`true`/`false`/`1`/`0` case-insensitively; numbers are
     parsed strictly, with a rejected trailing garbage rather than a
     silently truncated value. Subtype-specific wording (`up`/`down`,
     `open`/`close`) is **not** modelled in this slice.
6. **Add `DptValue` formatting** (spec E4-D9): a `Display` impl, or an
   explicit `format` method, producing the short human string the CLI
   prints (`on`, `off`, `-3.4`, `50 %`, `increase step 3`). Units appear
   only where the subtype's scaling makes the unit part of the
   conversion. Decide the float formatting rule — enough digits that a
   decoded value round-trips visually, without exponent noise — and state
   it in a comment.
7. **Tests** in `dpt/codec.rs`'s own `#[cfg(test)] mod tests`: per main
   type, a round trip (value → payload → value) at minimum, maximum,
   zero and one interior value; every reserved or invalid code the
   Standard defines; wrong-length payloads; out-of-range engineering
   values; unparsable text; and `UnsupportedDpt` for a main type this
   slice does not implement. Each test named for what it asserts, not
   `test_decode_1`.

**Done when:** the five gates pass; the APCI test from step 3 exists and
passes; `cargo test -p knx-core` shows the new tests; and nothing outside
`knx-core`/`knx-net` changed.

## Task 2 — the multi-octet datapoint types

**Files:** `crates/knx-core/src/dpt/codec.rs` only.

Implement main types **9, 12, 13, 14, 16, 17, 18** in the same shape Task
1 established, with the same test obligations, same citation obligation,
same error variants.

Points that decide correctness:

- **Main type 9** is the trickiest thing in this slice: a 2-octet float
  with a sign bit, an exponent and a mantissa, a documented "invalid
  data" code, and a documented resolution. Encode must pick the exponent
  the Standard's rule prescribes and must reject values the format cannot
  represent rather than silently losing them. Decode must return
  `InvalidData` for the reserved code rather than a number. A value that
  cannot be represented exactly is a rounding question the Standard
  answers — cite the answer.
- **Main type 14** is IEEE 754 single precision; state the octet order
  and cite it.
- **Main type 16** is a fixed-length character field. The character set,
  the field length and the padding rule all come from the Standard.
  Decode must not return trailing padding as content; encode must reject
  a string that is too long or carries characters outside the set rather
  than truncating or substituting.
- **Main types 17 and 18** have an off-by-one between the wire value and
  the scene number a human uses, and 18 carries a control bit. Get the
  direction of the off-by-one from the Standard and pin it with a test
  that would fail if it were inverted.
- **Main types 12 and 13** are the 4-octet unsigned and signed integers;
  state the signed representation and the octet order, cited.

**Done when:** the five gates pass, and every main type in the spec's
§4.1 "yes" column is implemented.

## Task 3 — group-address DPT resolution

**Files:** new `crates/knx-core/src/dpt/resolve.rs`,
`crates/knx-core/src/dpt/mod.rs`, `crates/knx-core/src/lib.rs`.

Implement `GroupAddressDpt` and `resolve_group_address_dpt` exactly as
spec E4-D6 specifies. The whole value of this function is in what it
refuses to do, so the tests matter more than the code:

- no linked communication object at all → `None`;
- one linked object stating a DPT → `Single`;
- two linked objects stating the *same* DPT → `Single`, not a
  one-element `Conflict`;
- two linked objects stating *different* DPTs → `Conflict` carrying both,
  sorted and deduplicated, and **never** a pick;
- an object whose `dpt` is `Override::Absent`, `Override::Empty` or
  `Override::Malformed(_)` contributes nothing — one test per state, with
  a comment recording that `Empty` means ETS deliberately cleared the
  value (ADR-0010) and is not the same as absent;
- links in both `Direction`s count;
- a group address id that does not exist in the project → `None`, not a
  panic.

Also provide whatever small helper the CLI needs to build a
`HashMap<u16, DptRef>` for a whole project in one pass — resolving per
telegram inside a monitor loop is the wrong shape (spec E4-D8). Decide
whether that helper belongs here or in the CLI and say why in the report;
if it lands here, it must be equally free of I/O.

**Done when:** the five gates pass and every bullet above has a named
test.

## Task 4 — wire it into `knx bus monitor` and `knx bus write`

**Files:** `apps/knx-cli/src/main.rs`, new
`apps/knx-cli/tests/cli_bus_dpt.rs`.

1. `bus write` gains `--dpt <DptRef>` and `--dry-run`, per spec E4-D7.
   Parse and validate everything — address, DPT, value — **before**
   opening a socket. `--dry-run` prints the address, the DPT and the
   encoded payload in a stable, greppable form, then exits `0` without
   connecting.
2. Resolution from `--project` when `--dpt` is absent: `Single` encodes;
   `None` and `Conflict` are errors that name what was found and tell the
   user to pass `--dpt`. Neither flag given → today's raw `0`/`1`/hex
   path, unchanged, and its doc comment updated to say it is now the
   explicit raw fallback rather than the only behaviour.
3. `bus monitor --project` builds the address → DPT map once at startup
   and decodes each telegram per spec E4-D8, printing the raw payload and
   a stated reason whenever decoding is unavailable or fails. Without
   `--project`, output is byte-identical to today's.
4. Update the `USAGE` string at the top of `main.rs` for both
   subcommands.
5. **Tests** in `apps/knx-cli/tests/cli_bus_dpt.rs`, following the
   existing harness in `apps/knx-cli/tests/cli_group_address_csv.rs`
   (build a tiny `.knxdb` through `knx-core`/`knx-store`, then drive the
   built `knx` binary). None of them may open a network socket:
   - `--dry-run --dpt DPST-9-1 1/2/3 21.5` prints the expected payload
     and exits 0;
   - `--dry-run` with a project whose group address resolves to a single
     DPT encodes using it;
   - a project whose group address has conflicting DPTs fails with a
     message naming both, exit non-zero;
   - a project whose group address resolves to nothing fails asking for
     `--dpt`, exit non-zero;
   - an unparsable value for the given DPT fails before connecting;
   - `--dpt` naming an unimplemented main type fails with the unsupported
     error.

**Done when:** the five gates pass, and every test above exists and
passes without a gateway on the network.
