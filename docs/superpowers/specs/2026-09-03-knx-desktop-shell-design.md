# Design: knx-desktop shell, projection layer, Project Explorer

Date: 2026-09-03
Session: 5 (UI/UX), cycle 1 of N
Status: Approved

## Context

[ROADMAP.md](../../ROADMAP.md) Session 5 goal is the desktop application:
`apps/knx-desktop` (Tauri shell + React), the projection layer
(`ProjectTree`, `DeviceList`, `GroupAddressTable`, `Inspector<T>` per
[ADR-0009](../../adr/0009-ui-boundary.md)), Project Explorer, properties
inspector, search, command palette, dark/light mode.

Session 5's entry condition — "import produces a model worth
displaying" — is met (Sessions 3/4 done). No frontend tooling exists yet in
this repository: this is the first cycle, scoped to the smallest slice that
puts a real project on screen.

`knx-store` has no entity persistence yet (only the opaque passthrough table
and the Session 4 manifest — see IMPLEMENTATION_STATUS.md). "Open project" in
this cycle therefore means: run the existing `.knxproj` import pipeline,
hold the resulting `knx_core::Project` in memory, display it. Saving to and
reloading from `knx-store`'s own format is explicitly out of scope here and
carried forward, same as it already was after Session 4.

## Goal (this cycle)

A user can launch the desktop app, pick a `.knxproj` file, and see its
topology and building hierarchy as a tree — the Project Explorer, without
Inspector/Search/Command Palette/theming, which are later cycles of the same
session.

## Decisions made during brainstorming

- Whole of Session 5 is decomposed into multiple cycles rather than one
  spec. This document covers cycle 1 only: shell + projection layer +
  Project Explorer.
- "Open project" is import-and-display only. No save/reload of knx-desktop's
  own state; no entity persistence work in this cycle.
- No UI component/styling library. Plain CSS and hand-built components,
  per CLAUDE.md's "avoid unnecessary frameworks" — the tree/table/inspector
  widgets this session needs are small enough to own directly.
- The projection layer is its own crate, `crates/knx-projection`, not code
  living inside `apps/knx-desktop/src-tauri`. It depends only on
  `knx-core`, has no Tauri dependency, and is unit-testable on its own.
- The store connection `knx_app::import_ets_project` requires is an
  in-memory `rusqlite::Connection`, migrated to
  `knx_core::CURRENT_SCHEMA_VERSION` and discarded when the session ends —
  consistent with "no persistence in this cycle."

## Architecture

```
apps/knx-desktop/
  src-tauri/     Tauri v2 Rust shell.
                 State: Mutex<Option<knx_core::Project>>.
                 Commands: open_project(path: String) -> Result<ProjectTree, String>
  src/           React + TypeScript + Vite. Plain CSS, no UI framework.
  src/bindings/  Generated by ts-rs from knx-projection's structs. Committed
                 to the repo; CI regenerates and diffs to catch staleness.

crates/knx-projection/    NEW crate.
  Depends on: knx-core only (not knx-app, not knx-etsproj, not knx-store).
  Pure function: build_project_tree(&knx_core::Project) -> ProjectTree.
  Every projection struct derives ts-rs's `TS` in addition to `Serialize`.
```

Data flow for "open project":

```
User picks file (Tauri dialog plugin)
  -> invoke("open_project", { path })
  -> src-tauri: open in-memory Connection, migrate to CURRENT_SCHEMA_VERSION
  -> knx_app::import_ets_project(path, &conn) -> ImportedProject { project, report }
  -> store project in Mutex<Option<Project>> app state (report is not stored;
     only its warning count is read before it is dropped)
  -> knx_projection::build_project_tree(&project) -> ProjectTree
  -> return ProjectTree to frontend
  -> React renders Project Explorer from ProjectTree
```

`check-layering` (xtask) gains a fourth root: `knx-projection` must not
reach `quick-xml`, `rusqlite`, `tokio`, or any other infrastructure crate —
mirroring the existing checks for `knx-core`, `knx-etsproj`,
`knx-productdb`.

This keeps ADR-0009 intact: the UI never receives `knx_core::Project`
directly, only the display-shaped `ProjectTree`, and all tree-building
(resolving `BuildingPart` id-references into actual nesting, bucketing
unassigned devices, etc.) happens in Rust before it ever reaches
TypeScript.

## ProjectTree shape

One tree per `Installation`, exposing both trees ETS itself shows side by
side — topology (Area → Line → Device) and buildings (recursive) — plus the
devices that belong to neither:

```rust
#[derive(Serialize, TS)]
struct ProjectTree {
    schema_version: u32,
    /// Count of ImportReport warnings. Never silently discarded per
    /// CLAUDE.md; drill-down into individual warnings is a later cycle.
    warnings: usize,
    installations: Vec<InstallationNode>,
}

#[derive(Serialize, TS)]
struct InstallationNode {
    id: u32,
    name: String,
    topology: Vec<AreaNode>,
    buildings: Vec<BuildingNode>,
    unassigned: Vec<DeviceNode>,
}

#[derive(Serialize, TS)]
struct AreaNode {
    id: u32,
    name: String,
    address: u8,
    lines: Vec<LineNode>,
}

#[derive(Serialize, TS)]
struct LineNode {
    id: u32,
    name: String,
    address: u8,
    devices: Vec<DeviceNode>,
}

#[derive(Serialize, TS)]
struct BuildingNode {
    id: u32,
    name: String,
    /// BuildingPartType as a string (e.g. "Room", "Floor") — the enum
    /// itself stays in knx-core; TS gets a plain string this cycle.
    kind: String,
    children: Vec<BuildingNode>,
    devices: Vec<DeviceNode>,
}

#[derive(Serialize, TS)]
struct DeviceNode {
    id: u32,
    name: String,
    /// Formatted individual address, e.g. "1.1.1" — None if the device has
    /// no address assigned (valid project state).
    address: Option<String>,
    description: Option<String>,
}
```

`build_project_tree` resolves `BuildingPart::children`/`::devices` id-lists
into actual nested `BuildingNode`/`DeviceNode` values, and
`Topology::areas`/`::lines`/`::unassigned` similarly — the frontend never
looks up an id, it only renders what it is given.

## Tauri commands (this cycle)

Only one command: `open_project(path: String) -> Result<ProjectTree, String>`.

No separate `get_project_tree` — nothing else needs to re-fetch the tree in
this cycle, so it is not added (YAGNI). Later cycles that need the live
`Project` again (Inspector, search) add commands as those cycles need them.

## Error handling

- Import failure (`AppError` from `knx_app::import_ets_project`): the error
  message is returned as `Err(String)`; the React side shows it in a
  dismissible banner. No retry logic.
- Import warnings: surfaced only as `ProjectTree::warnings`'s count, shown
  as a line in the Explorer's footer ("N warnings"). Full listing is a later
  cycle, once the Inspector exists to show them against something.

## Testing

- `knx-projection`: unit tests against hand-built `knx_core::Project`
  fixtures — empty project, a nested building hierarchy (building → floor →
  room → device), a device in `Topology::unassigned`, an installation with
  no buildings at all. Deterministic ordering (input order preserved, no
  implicit sorting) is asserted explicitly.
- `apps/knx-desktop/src-tauri`: one integration test that calls
  `open_project` against the reference `.knxproj` already in the repo, and
  asserts the resulting tree's device/area/line counts against the same
  golden values Session 3's import golden test already established (36
  devices, etc.) — a second, cheap check that the projection did not drop or
  duplicate anything the importer produced.
- No frontend test framework this cycle. Manual verification via `cargo
  tauri dev` (the `run` skill). Vitest (or similar) is added when a later
  cycle's interaction logic (search filtering, command palette) is
  complex enough to need it — not preemptively.

## CI

`.github/workflows/ci.yml` gains:
- A Node.js setup step (version pinned, matching whatever `apps/knx-desktop`'s
  `package.json` engines field states).
- `npm run build` in `apps/knx-desktop` (frontend compiles, `tsc` included).
- A ts-rs binding staleness check: regenerate bindings into a scratch
  location (or regenerate in place), `git diff --exit-code` against the
  committed `src/bindings/` — same shape as the existing `check-layering`
  gate.
- `knx-projection` added as a fourth root to `check-layering`.

## Out of scope for this cycle

Properties Inspector, search, command palette, dark/light mode, entity
persistence into `knx-store`, warning drill-down, `get_project_tree`/any
refetch command, a frontend test framework. Each is its own future cycle of
Session 5, not bundled in here.
