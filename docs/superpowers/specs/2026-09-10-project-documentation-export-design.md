# Project documentation export (HTML) — design

**Task:** T13 in `docs/GAP_ANALYSIS_ETS.md`. Closes gap **D4** ("No printing /
documentation export").

**Goal:** turn the open project into one self-contained HTML file that a user
can read in a browser, print on paper, or save as PDF through the browser's own
print dialog — topology, buildings, group addresses and devices, in a layout
built for reading rather than for round-tripping.

---

## 1. The honesty problem, stated first

ETS can print topology, building, device and group-address reports. This design
**does not claim to reproduce them**, because nothing in this repository
describes what they contain:

- `docs/RESEARCH.md` has no section on ETS printing or report layouts. Every
  "report" hit in that file is about *this* application's `ImportReport`
  (import diagnostics), which is a different concept entirely.
- `OriginalData/` holds three real `.knxproj` files and no ETS-produced report
  of any kind — no PDF, no printout, no exported document.
- The extracted KNX Standard corpus does not standardize a project-report
  format. Printing is an ETS *application* feature, not a KNX Association one.

Consequences that bind every part of this design:

1. The output is **"KNXBench project documentation"**. It is never labelled,
   described, or commit-messaged as an ETS report, an ETS-compatible report, or
   a replacement for one — in code, docs, UI text or CLI output.
2. Its content is chosen from **what this domain model actually holds**
   (§3), not from a remembered ETS layout. Where the model is thinner than a
   user might expect, the document says so in its own body (§5), not only in
   `docs/`.
3. This is the same rule `docs/KNOWN_LIMITATIONS.md` §38 applies to T12's CSV,
   and the same naming discipline `GroupAddressCsvButtons.tsx` already follows
   ("CSV", never "ETS CSV").

If an ETS-produced report sample is ever obtained, comparing content sets
becomes possible and a second layout could be considered. Until then, parity is
unmeasurable and therefore unclaimable.

## 2. Why HTML, and why only HTML

The backlog entry already picked the format and gave the reason — "HTML,
easiest to generate and to test deterministically" — and the reconnaissance
confirms the cost of the alternative: **there is no HTML, templating, or PDF
crate anywhere in the workspace today** (`askama`, `tera`, `handlebars`,
`maud`, `minijinja`, `sailfish`, `liquid`, `html-escape` — none appear in any
`Cargo.toml` or in `Cargo.lock`). This is a green field, not a
pick-the-existing-one decision.

So:

- **HTML is generated by hand**, with `write!`/`push_str` into a `String` and a
  pair of escaping functions (§4). `knx-csv` already generates its text format
  without a template engine; a document with a fixed section structure and no
  user-authored templates does not need one either. CLAUDE.md: avoid
  unnecessary dependencies.
- **PDF is out of scope.** Every browser prints to PDF, the document ships
  `@media print` rules for exactly that, and a Rust PDF renderer would be a
  large new dependency serving a button the operating system already has.
  Recorded in §9 and in `KNOWN_LIMITATIONS.md`, not silently omitted.
- **The file is self-contained**: one `.html` file, inline `<style>`, no
  JavaScript, no images, no web fonts, no external URLs of any kind. It has to
  survive being emailed, copied to a USB stick, or opened on a machine with no
  network. A test asserts the absence of `<script` and of `http://`/`https://`
  in the output, so this cannot rot.

## 3. What the document contains

Each section is derived from the model, and each names its source:

| Section | Source | Notes |
| --- | --- | --- |
| Header | `ProjectInfo` (`project.rs:143`) | name, project number, group-address style, completion, last modified, project start, ETS schema version, domain schema version, plus the caller-supplied generation timestamp |
| Contents | — | anchor list, one entry per section and per installation |
| Summary | counts derived from the walk | installations, areas, lines, devices, communication objects, group ranges, group addresses, building parts, parameter values |
| Topology | `Installation::topology` (`topology.rs:41`) | area (address, name) → line (address, name, medium ref, domain address, IP multicast, TTL) → device (individual address, name, description); plus a list of `Topology::unassigned` devices |
| Buildings | `Installation::buildings` (`building.rs:25`) | the flat parent/children list resolved into its real nesting, showing kind, number, name and each part's devices; plus any part whose `parent` does not resolve |
| Group addresses | `Installation::group_ranges` + `group_addresses` (`group.rs:12`, `:41`) | ranges nested main → middle, each address showing formatted address, name, `Central`, `Unfiltered`, and every communication object linked to it (device, object number, DPT, direction); plus addresses inside no range |
| Devices | `Devices` (`devices.rs:11`) | per device: name, individual address, description, commissioning state, product ref, program ref; then its communication objects with number, name, description, DPT and the layer it resolved from, the five flags, active state, and links; plus any orphaned communication object |
| What this report does not contain | — | §5 |

Three model facts shape this and are worth stating outright, because each is a
place where a reader might expect more than exists:

- **A group address has no datapoint type of its own** (`group.rs:33-39`); the
  DPT belongs to the linked communication objects, several of which may
  disagree. The document therefore **lists the linked objects with their
  individual DPTs** rather than printing one derived value. That is more
  information than a consensus value, it never has to guess, and it is a
  deliberately different computation from `knx-csv`'s `derive_dpt` — which
  answers "is there a unanimous DPT?" for a spreadsheet column — so no logic is
  duplicated between the two crates.
- **`product_ref` and `program_ref` are opaque strings** (`device.rs:27-31`).
  Resolving them to a manufacturer and product name requires `knx-productdb`, a
  separate database this crate must not reach (§6). They are printed verbatim
  and labelled as unresolved identifiers, with the reason in §5.
- **Parameter values are raw, uninterpreted strings** (`parameter.rs:1-5`,
  RESEARCH R3), and module arguments are opaque (`module.rs:1-5`). Neither gets
  a section; both are counted in the summary and explained in §5. Printing 1390
  raw `RefId`/value pairs would be volume without meaning.
- **Communication-object `size` is not shown.** It is never populated at
  instance level — `device.rs:63-65` documents the field as unstated in
  schema 11 and filled in only once a product database exists, and
  `infer.rs:178` sets it to `None` for every inferred instance. There is
  nothing to print yet; it becomes available once `knx-productdb` can
  supply it from the application program.

## 4. Determinism, escaping, and the two properties that must not rot

**Determinism.** The same project and the same generation timestamp must
produce byte-identical HTML. Two rules get it there:

- The generation timestamp is **passed in by the caller** as
  `generated_at: DateTime<Utc>`, never read from the clock inside the crate.
  Server, CLI and tests each supply their own; tests supply a fixed one.
- **No `HashMap` may drive output order.** Every ordered walk uses the model's
  own order — `Vec` order for installations, areas, lines, buildings, ranges
  and addresses; `BTreeMap` id order for devices and communication objects
  (`devices.rs:13-15`). A lookup index may be a `HashMap`; an iteration that
  emits document text may not.

A test generates the same report twice and asserts the two strings are equal —
which catches a clock read, and, with a project containing enough entities,
catches a `HashMap` iteration too.

**Escaping.** Two functions, applied at every insertion point:

- text content: `&` → `&amp;`, `<` → `&lt;`, `>` → `&gt;`
- attribute values: the above plus `"` → `&quot;`, `'` → `&#39;`

Names in a KNX project routinely contain `&` (`Licht & Steckdose`) and
occasionally `<`. Tests cover a device name, a group-address name and a
building-part name each containing `<`, `&`, `"` and `'`, and assert the raw
characters never reach the output unescaped.

**Anchors** are built from numeric entity ids (`device-<id>`,
`ga-<id>`, `installation-<id>`), never from names — so anchor generation needs
no escaping, no slugification and no uniqueness pass.

**Style.** One inline `<style>` block: a system font stack, plain borders,
no dark backgrounds (they waste toner and print grey), and an `@media print`
block that avoids page breaks inside table rows and starts each top-level
section on a new page. **The document contains no animation and no transition
at all** — which is how it satisfies the cross-cutting rule in
`docs/ROADMAP.md` ("Motion and animation": every animation must be switchable
off from inside the application). A printed page cannot offer a toggle, so the
only honest option is to have nothing to toggle.

## 5. The document states its own limits

The last section of every generated report is headed **"What this report does
not contain"** and lists, in the output itself:

- Manufacturer, product and application-program **names** are not resolved —
  the product database is a separate store and this generator does not read it;
  the raw reference identifiers are printed instead.
- **Parameter values** are stored uninterpreted and are not listed.
- **Module instance arguments** (schema ≥ 21 devices) are retained but not
  decoded.
- **Binary data** attached to devices is referenced by name and id only.
- Text is rendered in the project's **default language** only.
- This report is **not an ETS report** and has not been compared to one.

Putting it in the document, not just in `docs/`, is the same rule the rest of
this project follows for exports: the artifact travels without its
documentation, so the artifact carries its own caveats.

Anything the walk finds that is structurally odd is **both** rendered in the
document and returned as a warning to the caller: devices in no line, group
addresses in no range, building parts with a dangling parent, communication
objects owned by no device, links to a group address that does not exist, and
`Override::Malformed` values. CLAUDE.md forbids discarding these quietly, and a
document that omitted them would be lying about the project.

## 6. Where the code lives

A new crate, `crates/knx-report`, depending on `knx-core`, `knx-projection` and
`chrono` — and nothing else. This follows the same one-crate-per-output-format
precedent as `knx-csv`.

`xtask check-layering` gains a matching rule with two halves:

- `knx-report` must reach none of `knx-store`, `knx-etsproj`, `knx-productdb` —
  the `knx-csv` rule verbatim in shape.
- `knx-report` must reach none of `layering::CORE_FORBIDDEN` — a document
  renderer has no business with a database, an archive parser, or an async
  runtime.

**Why `knx-projection` is a dependency and not a duplication.**
`build_device_detail` (`crates/knx-projection/src/lib.rs:314`) already resolves
a communication object's text, description and DPT through the project's string
table and provenance layers, and already resolves its links to formatted
addresses. That is the fiddliest logic in the device section, and re-writing it
in `knx-report` is exactly the duplication CLAUDE.md forbids. `knx-projection`
is itself pure — no IO, no storage, held to the same `CORE_FORBIDDEN` rule as
`knx-core` (`xtask/src/main.rs:65-69`) — so depending on it costs no layering
purity.

What is *not* reused is `build_project_tree`: its `ProjectTree` drops
`Line::medium_ref`, domain addresses, `completion`, `BuildingPart::number`,
`product_ref`/`program_ref`, and flattens the group-range hierarchy — every one
of which this document wants. Topology, buildings and group addresses are
therefore walked from `knx_core::Project` directly, mirroring
`build_building_forest`'s parent/children reconstruction technique
(`lib.rs:396`) rather than calling it.

Public surface, pure — a `&Project` in, a `String` and typed warnings out, with
no knowledge of files, HTTP or SQLite:

```rust
pub fn render_html(project: &Project, options: &ReportOptions) -> HtmlReport;

pub struct ReportOptions {
    /// Supplied by the caller so the output is byte-deterministic in tests.
    pub generated_at: DateTime<Utc>,
}

pub struct HtmlReport {
    pub html: String,
    pub warnings: Vec<ReportWarning>,
}

pub struct ReportWarning {
    /// Where in the project, e.g. `"device 42"`, `"group address 1/2/3"`.
    pub location: String,
    pub detail: String,
}
```

There is deliberately **no section-selection option**. One report, all
sections, a table of contents to navigate it. Selective reports are a real
feature request the day someone asks for one; adding the knob before then is
the speculative abstraction CLAUDE.md warns about.

Internally the crate splits in two: `model.rs` builds the derived indices (the
building forest, the range nesting, the group-address → communication-object
inverse index, the orphan lists) and is unit-testable without looking at a
single angle bracket; `render.rs` turns `&Project` plus those indices into
HTML.

## 7. Surfaces

**Server** — one route, mirroring the `.knxproj` and CSV exports rather than
inventing a new shape:

- `POST /api/project/documentation-export` `{ path }` → `{ warnings }`, writing
  through the same `resolve_new_project_path` helper
  (`apps/knx-server/src/paths.rs:63`) the other two exports use, and mapping
  failure to `ApiError::bad_request` for the same reason export does — it only
  reads already-loaded state.

The route is named `documentation-export`, not `report`, because `report`
already means `ImportReport` throughout this codebase and the collision would
be permanent.

Warnings are pushed into the T11 session log inside the domain function, one
`LogEntry` per warning with `source: "doc-export"`, the way
`export_group_addresses_csv_impl` does (`domain.rs:503-513`) — not summarized,
not counted, each one individually. No `SessionLog::reset`: only opening a
project resets the log.

**CLI** — one subcommand over a `.knxdb` store, in the existing hand-rolled
argument style (this CLI has no `clap` and is not getting one):

```
knx doc-export <store.knxdb> <out.html>
```

It prints a human-readable summary and every warning, following
`print_export_report` (`apps/knx-cli/src/main.rs:465`). It exits `0` on
success and `1` when it could not produce a file at all; there is no exit-code
`2` case, because a report with warnings is still a complete and correct
report — the warnings describe the *project*, not a failure of the export.

**Web** — one button, "Export documentation…", in the same toolbar row as
"Export to .knxproj…" and the CSV buttons, using the existing
`pickSavePath` abstraction with an `html` filter and a one-line toast. The
detail goes to the Log tab T11 already built. No new panel, no preview pane.

## 8. Testing

- **`model.rs` unit tests** over hand-built projects (a `testutil.rs` in the
  style of `knx-csv`'s): the building forest nests correctly and puts a
  dangling-parent part in the orphan list; the group-range nesting picks the
  innermost containing range; the inverse index maps a group address to every
  communication object linked to it, in device-id order; a communication object
  owned by no device lands in the orphan list; a link to a non-existent group
  address is reported.
- **`render.rs` unit tests**: two identical renders are byte-equal;
  `<`, `&`, `"` and `'` in a device name, a group-address name and a
  building-part name all arrive escaped; the output contains no `<script` and
  no `http://`/`https://`; every device, group address and building part in a
  small project appears exactly once; the "What this report does not contain"
  heading is present; the `@media print` block is present.
- **Corpus-gated integration test** — in `crates/knx-app/tests/`, **not** in
  `knx-report`, because `check-layering` walks dev-dependency edges too
  (`xtask/src/layering.rs:94-98`), so a `knx-etsproj` dev-dependency on
  `knx-report` would trip its own rule; `knx-app` is deliberately the one crate
  that sees both sides (`xtask/src/main.rs:41-45`). Guarded by the standard
  skip-if-absent block, it imports the reference `.knxproj`, renders the
  report, and asserts: every one of the project's group addresses appears in
  its formatted form; every device name appears; the counts printed in the
  summary equal the counts computed from the `Project`; and the output parses
  as balanced HTML to the extent of having equal `<table>`/`</table>` and
  `<tr>`/`</tr>` counts.
- **Server test** for the route including the "no project open" rejection and
  the session-log entries.
- **CLI test** driving the built binary against a tiny hand-built `.knxdb`.
- **Frontend tests** for the button: cancelled picker calls nothing, a
  successful export reports the warning count, a rejected export surfaces the
  error.

## 9. Out of scope, and recorded as such

- **PDF generation in Rust** — the browser's print dialog does it (§2).
- **ETS report parity or comparison** — no sample exists (§1).
- **Product/manufacturer name resolution** — needs `knx-productdb`, which this
  crate must not reach (§6). A future task could pass an already-resolved
  lookup table in through `ReportOptions`.
- **Parameter and module-argument listings** — the values are uninterpreted
  (§3).
- **Section selection, filtering, or a custom cover page** (§6).
- **Multiple languages in one document** — the project's default language only.
- **Word/ODF/Markdown output.**
- **A print preview inside the application** — the browser has one.
