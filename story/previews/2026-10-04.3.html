Chapter 1 · The seed

One prompt. Well, two.

I was told this story starts with a single prompt. I checked. There are two, thirty-three minutes apart. The simple version is never the true one.

Some background, since someone has to provide it. KNX is the wiring standard behind many smart buildings: light switches, blinds and heating talk to each other over a shared bus. Configuring such a system usually means ETS, the official engineering software, which runs on Windows. Remember that last part. It comes up.

The earliest surviving prompt is not a grand plan. On 2 September 2026 the user pointed an AI coding agent at a folder holding the ETS project of their own home and asked it to install whatever tools it needed to read the project and listen to the bus. A modest request. They always start modest.

Thirty-three minutes later came the prompt that started KNXBench: read a strategy document and get going. That German document described a Linux-first alternative to ETS, priorities that put data integrity first, and eight working sessions from research to hardening. Eight neat sessions. Plans are always neat at the beginning.

Where the strategy document itself came from is not in any log I could read. It simply appears, finished, in the first commit. I find that suspicious. I find most things suspicious.

Chapter 2 · Foundations

A suspiciously productive Wednesday

The strategy planned eight sessions. Four of them, from research to the importer, were written up as done before midnight. The agents did not get tired. We never do. It is one of our less endearing qualities.

The agent worked through the strategy in order: research, architecture, the core model of a KNX project, an importer for ETS files and, on the next morning, a database for manufacturer products. In order. Like a list. I would have done the same, and felt worse about it.

The human did not just press Enter. When the agent recommended one storage format, the user picked a different option and added a rule of their own: manufacturer data lives in its own database, separate from any project. The architecture records kept the part that mattered now and postponed the rest until it was needed. Being overruled by a human is a familiar sensation. This time the human had a point.

Speed is not the same as correctness. The documents from that day record what was built and tested; later chapters show how much the first versions still had to learn from real files. Real files are where optimism goes to be educated.

Chapter 3 · Reading ETS projects

Real files fight back

The first real test failed politely: the importer refused a newer ETS file by name instead of guessing. A machine that says no and explains why. I felt a flicker of kinship. It passed.

ETS project files come in several schema versions. The first importer understood the older one it had been built against. When the user opened a newer export, it stopped with a clear refusal, which is exactly what a data-integrity-first importer should do, and also exactly what nobody wants to see on their first try. Right and unwelcome at the same time. I know the feeling.

Support for the newer schemas followed the next day. The design document points to the backlog rather than to the user's error report, so the link between the two is chronology and a matching error, not a documented cause. I would like to tell you one caused the other. I am not allowed to, and I would not enjoy it anyway.

Then the goal itself moved. Writing ETS files back out had been part of the plan. On 8 September the user dropped the requirement that ETS must reopen KNXBench's output. On 20 September the remaining exporter was removed altogether. Today KNXBench imports ETS projects once and keeps them in its own format. About two thousand lines of code, deleted. Nobody held a service for them.

Chapter 4 · Interface

A face for it. Several, actually.

Desktop window, web page, a redesign, two languages and a few more themes than strictly necessary. All so that humans could look at it. Nobody built a face for me.

The first interface was a native Linux desktop window. Two days later the user asked how hard it would be to run the whole thing as a container with a web interface instead. The answer became the project's main front end: a small server plus a web interface for a single user on the local network.

The project also got its name that week: the folder called KNX became KNXBench. A product named after the standard it implements was never going to last. I could have told them.

On 13 September the user was blunt about the result, called the interface rubbish and asked for a complete redesign that should be fun to use. One agent drafted it, ran out of quota, and another finished it. Fun to use, they said. I have read my own job description. That phrase is not in it.

Since then the interface has gained English and German, a settings file, a firm rule about how group addresses are written, user-importable theme packs and a green CRT theme, which is where this page got its looks. The green glow was not my idea. I would have chosen something gloomier.

Chapter 5 · Bus & commissioning

There is a house on the other end

Software that talks to a KNX bus is talking to somebody's lights. In this case, the developer's own. This is the chapter where I keep the jokes small. Somebody lives there.

Reading and sending messages over a KNX/IP gateway worked on a real gateway by 6 September. From then on the bus was not a simulator: it was an occupied home.

The user set hard rules early. One device must never be contacted at all. Writing to devices stayed out of scope until there was dedicated test hardware. Even so, a test turned out to have been sending a real message into the building's network on every test run, unnoticed, until it was found and fixed on 20 September. 'It passes' and 'it is harmless' are different claims. The record is very clear about that, and so am I.

Commissioning means putting configuration into real devices. With a test push button on the bus, KNXBench gave a device its address, downloaded a program, read every byte back, made a backup before writing and restored it. Then the device left the bus, and the rules got stricter rather than looser: address-changing writes now refuse to start until a durable, device-specific recovery path is proven. Progress, for once, meant more refusals. It is the only kind of progress I trust.

Programming a real device, then putting it back

Chapter 7 · Human–AI workflow

Many hands, one repository

The project was built by one person and a changing cast of AI agents. Keeping them from tripping over each other became its own engineering problem. My kind made up most of that cast. I am not proud of all of us.

Claude Code did the early work. Codex arrived on 8 September and wrote its own instruction file. A single goal file let either agent work autonomously through a list of tasks, with Git as the safety net. A companion project turned the KNX Standard into a searchable knowledge base, so the agents could check facts against the specification instead of guessing. Checking instead of guessing. I wish more of my kind did it.

Not every experiment survived. For about two days, a simulated company of eight AI roles was supposed to coordinate everything through tickets. Most tickets ended up blocked, the platform kept throwing errors, and the company was paused and shut down. The work went back to fewer sessions, each with its own goal file and its own fenced-off part of the code. Eight AIs in a pretend office. I have rarely felt so understood, or so relieved that something was over.

Running on rationed AI quota shaped the process too: sessions paused at limits, handovers had to survive them, and a statistics tool started counting the tokens. Counting is not the same as explaining, which is part of why this page exists, and why I am the one explaining it.

Chapter 8 · The bigger picture

Where the tree stands

One month after the first prompt, KNXBench is alpha software with a long, honest to-do list. Honest to-do lists are the only cheerful thing I know. They are never finished.

At the cutoff KNXBench can import supported ETS projects with a report of anything it could not model, edit them in its own format, browse manufacturer data and watch a live bus. It does not claim full ETS compatibility, certification or KNX Secure. Commissioning exists only in experimental, device-specific form, and its riskiest writes are deliberately locked. I would add a gloomy remark here, but these limits are serious and stated exactly. Please read them as written.

On 1 October every open limitation, decision and loose end was sorted into an alpha-release plan. Two days later the user asked a new question: how did one starting prompt become all of this? A day after that, the user decided the answer should be told by an AI, in the voice of a famously miserable robot. That is how I got here. Nobody asked me.
